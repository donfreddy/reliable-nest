# Identity Model

Three identifiers, three different scopes. Conflating any two of them is the
single most common way to break the guarantees in
[`guarantees-and-failure-modes.md`](guarantees-and-failure-modes.md).

| Identifier | Scope | Generated by | Stability | Used for |
| --- | --- | --- | --- | --- |
| `messageId` | Internal, globally unique | The framework, at enqueue time (UUIDv7) | Immutable across every retry | Outbox primary key, inbox dedup key, identity seed |
| `key` | Application/domain, not unique | The caller (optional) | Domain-defined | Correlation, grouping, debugging (e.g. `order.paid:ord_123`) |
| `idempotencyKey` | External, per call site | The framework, derived | Deterministic: same `(messageId, effectName)` always yields the same key | Forwarded to third-party SDKs (`Stripe-Idempotency-Key`, etc.) |

`key` is never a deduplication identity. Two different messages
(`invoice.paid` and `invoice.refunded`) can legitimately share the same
`key` (`invoice-123`); deduplication must always key off `messageId`.

## Deriving `idempotencyKey`

```ts
idempotencyKey = uuidv5(namespace = RELIABLE_NAMESPACE, name = `${messageId}:${effectName}`)
```

Implemented in `packages/core/src/identity.ts` as `deriveIdempotencyKey`.
Property-tested in `packages/core/test/identity.spec.ts` for:

- determinism: same inputs always produce the same output;
- independence from the clock: no `Date.now()` anywhere in the derivation;
- distinction by `effectName`: two different external calls in the same
  handler for the same message never collide on the same key;
- distinction by `messageId`: two different messages for the same effect
  never collide.

`attempts` is deliberately excluded from the derivation. Including it would
make every retry look like a brand-new operation to the provider, defeating
the entire point of forwarding an idempotency key.

## Recipes: idempotency by destination

`deriveIdempotencyKey` gives you a stable value. What you do with it depends
on what the destination actually enforces. A key nobody checks does not
prevent duplication by itself.

| Destination | Idempotency mechanism | Notes |
| --- | --- | --- |
| HTTP API (Stripe, payment providers) | Provider-recognized idempotency header | Only works if the provider actually enforces it server-side. Verify, do not assume. |
| S3 / object storage upload | Deterministic object key (e.g. `reports/{messageId}.pdf`), optionally checksum-verified | A retry overwrites the same logical object instead of creating a duplicate. |
| Email | Provider idempotency key if supported, otherwise lookup by correlation id | Without either, rare duplicate delivery is possible after an ambiguous timeout. Document this, do not hide it. |
| Message broker (Kafka, RabbitMQ) | Stable message id + consumer-side deduplication | The broker guarantees at-least-once at best; the consumer inbox does the actual dedup. |
| Search index / read model | Upsert by stable document id, versioned | Coalesces redundant reindex requests instead of racing them. |
| Local filesystem | Deterministic path + atomic replace (write to temp, rename) | A retry safely replaces the same artifact. |

The pattern is the same everywhere: `idempotencyKey` identifies the
operation, but the destination's own uniqueness boundary is what actually
makes repeating it safe. Reliable cannot impose idempotency on a provider
that does not support it, and it does not try to.

## Payload schema evolution

`payload` is stored as opaque `jsonb`; the framework does not version it.
Long-lived pending or dead messages can outlive a deployment that changes the
producer's payload shape. If that matters for a given message `type`, encode
a version explicitly in `headers` (the same field already used for
`traceparent`), and have the handler branch on it. This is an application
convention, not a framework feature: adding a dedicated column for it would
constrain every consumer to a scheme most of them do not need.
